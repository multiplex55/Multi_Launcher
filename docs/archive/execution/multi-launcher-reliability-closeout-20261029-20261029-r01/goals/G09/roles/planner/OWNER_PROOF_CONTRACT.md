## Deterministic acceptance contract

1. An entered-worker channel/barrier establishes that work is outstanding. While held, cancellation/close must return without waiting; no sleep or elapsed-time threshold is evidence of completion.
2. Duplicate Finder retains its single active slot after cancellation. Refused start/reopen attempts do not advance generation or start another job. Close invalidates all old progress/results and keeps reopen blocked until the matching post-join receipt.
3. Screenshot direct cancel drains and discards a late synthetic image; scheduling while draining fails. Shutdown transfers ownership nonblockingly, rejects subsequent schedules, and a captured reaper probe stays false while the worker is held. A callback/receipt after real join is the positive retirement evidence.
4. Use the existing reaper test that deliberately drops its notifier before the worker exits to prove that notification cannot publish an after-join receipt. Keep the worker held, assert callback absent, release it, then receive the actual callback. This is a controlled reaper ordering test, not a model of normal native cleanup.
5. Clear already-terminal Activity history before a delayed retirement update; the stale update must not recreate the row or affect a newer operation. Preserve live operations across clear. Never require a terminal label before work has returned merely because cancellation was requested.
6. Every blocked fixture has release-on-unwind cleanup and a bounded completion wait. Bounded retrying of the actual owner/probe predicate may service the owner, but a timeout, spin count or published result cannot substitute for the predicate. No idle polling is added to production.

## One supported native handle case

Reuse `src/duplicate_finder/tests.rs::activity_baseline_native_file_scan_cancel_and_warm_reopen`, `DuplicateFinderSession::with_wake_and_first_read_checkpoint`, and `src/duplicate_finder/content.rs::{FirstReadCheckpointGate,NativeContentReader}`. `NativeContentReadBackend::open` has already called `file_operations::open_duplicate_discovery_content_file` and owns `DuplicateDiscoveryContentFile` when the gate waits. The gate is **before** `self.file.read(buffer)`, not inside a blocked OS read.

Use only small synthetic identical files in a unique task-owned fixture under `target/productivity_expansion/activity_retirement/`. Before starting, verify each fixture supports a read open with `std::os::windows::fs::OpenOptionsExt::share_mode(0)` and immediately drop that probe. At the reader checkpoint, probe those same files again: at least the held source must refuse with `ERROR_SHARING_VIOLATION` (32), not a generic failure. Keep the gate held through cancel and close, require a false reaped probe and `WorkerRetiring` on reopen, and confirm the same held file still refuses the exclusive probe. After gate release, require the successful owner post-join/reopen receipt, then exclusive opens of every fixture must succeed. Drop probes before a warm scan; require the existing duplicate result, close/join again and clean the fixture.

This probes the production Windows file acquisition/RAII path and its join-bound release. Ordinary successful delete/rename is insufficient because `DuplicateDiscoveryContentFile` permits sharing for read/write/delete. The Rust extension sets Windows sharing mode; Windows rejects a requested share mode that conflicts with access on an existing handle. See [Rust OpenOptionsExt](https://doc.rust-lang.org/std/os/windows/fs/trait.OpenOptionsExt.html#tymethod.share_mode) and [Microsoft CreateFileW sharing rules](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew). These primary sources were read during planning; the proposed fixture was not executed.

This native case does not establish in-flight `ReadFile` interruption, worst-case filesystem latency, COM apartment cleanup, real screen capture cleanup, every native handle in the application, or global retirement. Screenshot injected captures remain deterministic lifecycle evidence only. Those unclaimed native categories are `NOT_RUN`, not inferred from another goal's automation limitations.
