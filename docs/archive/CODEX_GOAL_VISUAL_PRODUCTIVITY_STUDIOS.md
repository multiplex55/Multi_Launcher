## A0. Mandatory chained Git branch bootstrap — before any application work

**Hard requirement, repeated here independently of the Kickstart:** This one Goal/Kickstart pair defines **six explicitly separate, sequential work categories** (C01–C06). Create **one new, unique branch per category**. The Goal and Kickstart do **not** get separate branches. The following category's new branch MUST start at the preceding category branch's **actual final committed tip**, including all accepted earlier work, **never from master/main again**. There are no per-checkpoint branches, separate agent branches, Git worktrees, secondary clones, intermediate merges, rebases, or cherry-picks to advance the chain. Each category begins with a fresh `M0-A` baseline commit, followed by a single best-effort initial push, before application code work.

For **C01/M0-A**, and again at **every subsequent category's M0-A**:

1. Read `AGENTS.md`, this entire Goal, the Kickstart, relevant local instructions, and the prior category/goal's final execution record. Perform read-only checks: `git status -sb`, `git branch --show-current`, `git rev-parse HEAD`, remotes/upstream, dirty/untracked files, and recorded predecessor branch and `final_tip_sha`.
2. Identify the exact **`parent_branch` and `parent_tip_sha`**. If continuing an existing sequence, the required parent is the last completed goal/category's committed final tip—even if master advanced or the current checkout is elsewhere. If it exists only on the remote, fetch safely and verify exact identity. If there is **no prior goal in a genuinely new chain**, use the current up-to-date primary integration branch only after inspecting its actual state. Never silently substitute master when the predecessor is ambiguous/unavailable; record a blocker.
3. Protect unrelated user changes: do not `reset`, `stash`, `rebase`, `merge`, `pull --force`, force-checkout, discard, or stage unrelated files. If switching to the exact required tip is unsafe because of dirty work, stop and report the blocker instead of changing ancestry. No worktrees (`git worktree add/move/prune`), auxiliary checkouts, or secondary clones. All write operations use **one existing checkout, sequentially**.
4. Create a unique, idiomatic branch from that **exact SHA**, e.g. `git switch -c feat/visual-studios-01-quick-tools <parent_tip_sha>`, then verify HEAD matches it. At the category boundary use analogous names for `02-calculation-pad`, `03-date-time-studio`, `04-diagram-mermaid`, `05-regex-visualization`, `06-markdown-studio` (append a unique suffix if names already exist).
5. Create category **M0-A baseline** as a **new commit**, preferably a minimal task-specific execution ledger amendment; an intentional empty commit with `git commit --allow-empty -m "chore: [C01/M0-A] establish quick-tools category baseline"` is permitted. Do not accidentally stage pre-existing changes. Record `baseline_sha` independently of `parent_tip_sha`; verify `git rev-parse <baseline_sha>^` equals `<parent_tip_sha>`.
6. Attempt exactly one ordinary upstream push (`git push -u origin HEAD` where appropriate). If unavailable/rejected, retain the local commit, record the actual reason, and **continue locally** without retries, force pushing, or bypassing approval. After each later verified checkpoint commit, attempt one ordinary best-effort push. Push failure is not a code blocker.
7. At each category completion record `parent_branch`, `parent_tip_sha`, category branch, `baseline_sha`, checkpoint SHAs, `final_tip_sha`, push status, and working-tree state. The **next category MUST create its child branch from that exact `final_tip_sha`**. Do not carry accidental uncommitted source across boundaries. If incomplete/unsafe candidates remain, remove them safely without touching pre-existing user files; archive only bounded evidence/verified safe work and label the feature incomplete rather than handing off unverified behavior.

## A. Desired outcome

Deliver **six distinct, keyboard-friendly, visibly useful productivity enhancements** while retaining Multi Launcher's current fast single-query workflow:

1. **Quick Tools dashboard layout:** tool-specific row/column settings in Dashboard Editor; predictable responsive wrap and **all actions reachable**, even in cramped slots.
2. **Calculation Pad plus meaningful Converter improvements:** a multi-line editable calculation document with variables/dependencies and live results; improve the existing Convert panel into a polished, searchable, copyable unit/base converter.
3. **Date & Time Studio:** date arithmetic through a visual interface with pickers, difference/offset modes, and an offline, DST-correct time-zone comparison view.
4. **Editable Diagram and Mermaid Studio:** an independently usable **floating native window** with a visual graph canvas and synchronized text/preview for a **documented supported Mermaid flowchart subset**; persistent editable documents and PNG/SVG/Mermaid exports.
5. **Regex Visualization Studio:** extend the *existing* Regex Tester with an interactive syntax diagram and a bounded visual pattern builder using its current Rust-regex engine and tests/presets.
6. **Markdown Live Editor + clean Notes improvements:** a dedicated live split editor with export and reusable content blocks, while most shared editing/preview capabilities can be invoked contextually from Notes without replacing Notes' familiar light UI.

**Approved choices:** Q1 **A** (hybrid visual/Mermaid with safe, documented subset synchronization), Q2 **A** (shared editing capabilities with **separate interfaces**, Notes remains lightweight). No workspaces or desktop-wide pointer-navigation features; no "Act on this" project.

A completed feature must work in the running Windows UI, not merely compile or exist as domain data. User does **one** manual review only after Codex's autonomous verification is finished.

## C. Approved functional and UX requirements

### C01 — Quick Tools responsive internal grid

- Dashboard Editor must expose **Preferred columns** and **Visible rows** for `Widget: quick_tools` using the existing widget-specific settings UI (with concise help explaining these are *inside* the dashboard slot). Defaults reproduce current practical behavior as closely as possible for legacy configurations; existing `queries` as legacy string or `{query,auto_submit}` entries must deserialize and act unchanged.
- Arrange valid tools row-major in up to preferred columns, with stable source order and a practical minimum cell width. Reduce effective columns when the slot narrows; never draw buttons beyond the viewport horizontally, never silently discard extra actions. If count exceeds visible-row preference or available height, use the dashboard's **scrollable** overflow behavior (or a compatible clearly contained internal scrolling area) with discoverable scrolling, not hidden/inaccessible buttons. Do not let a `Clip` slot silently invalidate this tool's visibility promise; expose a safe non-destructive escape (e.g. editor warning/override to `Auto` after confirmation, or tool-specific inner scroll) while preserving non-Quick-Tools slot behavior.
- Keep labels readable (truncate with hover/full text where necessary); prevent overlapping, zero-width buttons or endlessly growing native windows. Maintain keyboard focus/Tab, stable Jump hints for duplicate entries, visible-target-only hints, and distinction between manual `query:` and auto-submit `queryexec:`.
- Reordering, removing, updating, adding and resetting tools must preserve settings consistency and existing saved data. Coverage includes 1, 2, many items, long Unicode labels, duplicate actions, narrow/wide slots, DPI/text scaling, scroll and resize.

### C02 — Calculation Pad + Converter

- **Calculation Pad:** a new launcher-discoverable standalone editable scratchpad (e.g. `calc pad`) with multiple labeled lines, comments, expressions, named values/variables and references to earlier result lines. Recalculate dependent lines when source changes; display errors by line without overwriting original input. Support decimal arithmetic, parentheses, useful operators/functions allowed by a documented deterministic grammar; reject cycles, unknown variables, division/nonfinite results and oversized expressions. Preserve source line order; no general-purpose scripting, network execution or arbitrary function calls.
- Distinguish scalar results from unit-valued results. Provide a small documented unit-aware workflow that **uses the existing unit conversion catalog** for valid conversions; do not silently treat dimensionally incompatible units as interchangeable. Keep first release scope to known physical units and base-number conversion supported by current code; no online/live currency, full symbolic CAS, general unit algebra or spreadsheet grid.
- Explicit Create/Open/Save/Save As for app-owned scratchpad documents with versioning, conflict detection, safe atomic publication and unsaved-change prompts. A blank scratchpad is usable without requiring a saved file. Copy a single formatted result or the full results summary without automatically writing clipboard on every keystroke.
- **Converter UX:** make the current panel resizable within practical bounds; show clear input-validation/errors, From/To selectors with search/favorites, Swap, useful multiple-target conversions within a category, direct Copy for selected results, precision/format controls, approximate-unit badges and stable keyboard focus. Retain existing categories, alias/casing rules and unit semantics, and the existing `conv`/`convert` command paths. Favorites/format preferences persist safely only when explicitly saved according to existing settings patterns.
- Preserve `CalculatorPlugin` `=` result/history behavior and `save_on_enter` policy: the Pad's live evaluation must not repeatedly append calculator history or launch/copy anything. Reuse shared pure number formatting where suitable; do not fork inconsistent evaluators for existing commands.

### C03 — Date & Time Studio

- Add a new discoverable date/time utility (a specific `date studio` opener checked *before* the existing free-form `date <expression>` parsing) with tabs or mode selector: **Between**, **Add/Subtract**, **Time zones**, and **Schedule preview** (bounded initial schedule interpretation, not a full recurrence engine).
- Between: choose start/end date and optional time with keyboard-editable fields and graphical calendar/time pickers. Display signed difference in days, weeks and relevant calendar units; avoid equating calendar months with fixed 30-day months. Add/Subtract: choose anchored date/time plus structured calendar units; show final date, weekday, and exact formatted interpretation, with copy action.
- Time zones: offline named IANA or equivalent authoritative zone rules and explicit timezone labels; show same *instant* across zones, daylight-saving transitions, ambiguous local times and nonexistent local clock times. Never silently guess a nonexistent DST time; ambiguous choices should be disambiguated or produce a clear explanation. Do not misuse simple numeric UTC offsets across daylight-saving changes. A dedicated data dependency is acceptable only when justified and locked.
- Schedule preview: show a bounded list of occurrences for a simple daily/weekly rule, with next-date selection and an explicit option to prepare an existing calendar entry or alarm when supported. **No automatic alarm creation, recurring automation, broad calendar rewrite or altered timer/alarm parser**; defer timer/alarm time-picker recovery unless already accepted in separate task.
- Keep existing `date` command outputs, local date arithmetic behavior, timezone-independent rules and `timer`/`alarm` control semantics unchanged. Preserve explicit copy/save and relative-time reference snapshot determinism while editing.

### C04 — Editable floating Diagram + Mermaid Studio (approved Q1 A)

- A launcher command opens an **independent floating/native child viewport** of the running application; once opened, it remains interactive if the main launcher is hidden. Closing Studio does not quit Multi Launcher, interfere with launch/hotkeys, or leave a zombie viewport. Respect DPI changes, focus, Escape, close/reopen and window lifecycle. Use existing native viewport ownership, with an honest embedded fallback only if platform support makes native unavailable; do not call it independent in that fallback.
- Provide a persistent **canonical visual graph document** with stable node/edge IDs, positions, edge labels, supported shapes, group/subgraph membership, and revision/undo information. Edit via pointer and keyboard: add/remove/rename nodes, connect/reconnect edges, drag to move, snap to grid, pan/zoom, selection, multi-select, undo/redo and simple auto layout. Provide flowchart templates (linear, decision, process). Constrain dimensions and document counts to keep interaction responsive. A property editor avoids cramped canvas-only manipulation.
- Hybrid text mode has editable Mermaid source on one side and preview/canvas on the other. **First shipping scope is a documented Mermaid flowchart subset**, e.g. `flowchart TD/LR` nodes (rectangular, rounded, diamond), directed connections and labeled edges, and support for basic subgraph grouping if feasible within the accepted model. Do **not** claim universal Mermaid compatibility, arbitrary JavaScript rendering, class/sequence diagrams, or perfect roundtripping of all Mermaid grammar. Validate source before publishing visual changes; syntax errors leave previous good model clearly labeled **stale** and preserve the full source draft. Unsupported constructs must remain in source, with precise diagnostics, and must never be silently discarded when switching views or saving.
- In the *supported subset*, editing source updates the graph and editing the graph produces corresponding parseable Mermaid with equivalent IDs/edges/labels and documented normalization. Treat preservation of unknown/unsupported constructs as an explicit gate: either keep original source unmodified and block incompatible visual edits, or require an overt, reviewable conversion; never transform data destructively without informed confirmation.
- New/Open/Save/Save As with a versioned editable document and explicit Mermaid `.mmd` import/export. Native editable format should preserve layout (plain Mermaid cannot represent arbitrary diagram coordinates); support **PNG and SVG export** from the accepted scene, with bounded render dimensions and escaped labels. Export does not implicitly overwrite source files; handle bad paths and concurrent edits. No background server, HTML script execution, or remote Mermaid CDN loading. If a third-party Mermaid renderer/parser is considered, justify behavior, offline availability, licensing, and safety before adding it.
- Include focused examples and direct runtime visual proof of nodes, arrows, label editing, a round-trip, import/invalid/unsupported source, export, focus, hidden-launcher and restart persistence.

### C05 — Regex Visualization Studio

- Extend **the existing Regex Tester** with a collapsible **Visualize** area (not a new competing tester). Render a navigable syntax/structure view based on its existing `regex_syntax` AST and `explanation.rs` spans: literals, character classes, groups, alternatives, repetitions, anchors. Selecting a node highlights the exact pattern span and its existing explanation; selecting syntax highlights the graph node. A visual constructor/palette can insert supported expression components into the existing regex draft and preview resulting Rust regex.
- Distinguish **syntax structure** from a literal engine execution trace. Do not invent an NFA/backtracking animation or pretend Rust regex supports lookarounds/backreferences. Invalid or unsupported patterns must show helpful diagnostics, preserve existing draft and last-valid visualization if used, and never claim a valid match. Use stable references on edit and meaningful focus/navigation order.
- Preserve existing flags, Unicode semantics, capture highlights, match counters, test cases, substitution previews, examples, bounded evaluation, history and saved preset schema. If a visual edit affects the draft, call the existing session's revision/invalidation/debounce path; never bypass evaluation policy or persist test text implicitly. Bound diagram complexity and avoid rebuilds each GUI frame when pattern/revision unchanged.

### C06 — Standalone Markdown Live Editor + Notes improvements (approved Q2 A)

- Add a discoverable **Markdown Studio** for user-selected `.md` documents with a resizable, keyboard-friendly Edit/Preview/Split interface, navigable outline, live rendering, formatting toolbar/shortcuts, table insertion/editing, code fences, links/images, and reusable **block templates** (snippets inserted into the document, not live linked to mysterious external mutable content). Provide explicit Open/New/Save/Save As, unsaved-change prompts, external-modification conflict handling, bounded large-document behavior, and non-destructive recoverable edits/undo.
- Direct export includes **Markdown source** and **standalone HTML** with reasonable local formatting and safely handled links/assets. The native `.md` remains the authoritative editable source. No full WYSIWYG guarantee, cloud sync, generic CMS, document-layout engine, or implicit arbitrary remote asset requests. HTML must be safely escaped/sanitized; no unsanitized executable script or raw untrusted HTML introduced by new export functionality. If PDF printing is readily supported it may be exposed as an explicit system Print/Save as PDF workflow, but a custom PDF renderer is **not** required for acceptance.
- Reuse `egui_commonmark`, `notes_markdown` parsing and pure formatting/preview helpers where compatible. Add a supported **Mermaid fenced block preview** using the accepted C04 native supported flowchart subset; invalid/unsupported Mermaid fences show source and diagnostics rather than disappearing. Allow explicit **Open Diagram in Diagram Studio** with a safe, reviewed transfer that does not silently alter the note; edits are incorporated only through an explicit user operation, maintaining existing note save and undo rules.
- **Notes stays separate and clean:** keep its existing Edit/Preview/Split, note title, backlinks, aliases, todo links, image assets, Find/Replace, templates, autosave and close/discard behavior. Add most useful shared authoring capabilities via a **collapsed/optional Markdown tools menu** and contextual table, code, formatting, block insertion, preview and export controls—do not cover the note editor with a permanently expanded Studio toolbar. Do not create a second Notes store or change existing note URL/link semantics.
- Test cross-surface parity for common Markdown, Unicode, tables, links, callouts, task lists, fenced code and Mermaid, with regression tests for concurrent note changes, unsaved drafts, missing assets and large documents. Native proof must demonstrate both interfaces and ensure Notes remains uncluttered by default.

## D. Scope boundaries and invariants

**Included:** the six approved categories and their directly necessary shared helpers, UI entry points, versioned app-owned data, documentation, and focused regression tests. One program, six sequential category branches, one cumulative final integration boundary.

**Excluded:** fixing old size persistence/Unicode inspector/ZIP safety, redesigning global search ranking, changing paste-sequence/hotkey ownership, a general workspace system, standalone web browser, automatic OCR, cloud services, untrusted JS execution, full Mermaid grammar, spreadsheet engine, full symbolic CAS, recurrence scheduler, compiler benchmarking initiative, broad app refactor or arbitrary plugin execution.

Protect: launcher hotkey + search focus, existing query/`=`/`conv`/`date`/`regex` routes and action payloads, dashboard configuration migration, Jump Mode hint/focus/Enter semantics, note link/todo/image contracts and save/undo policies, regex test/preset compatibility, independent viewport cleanup, Windows DPI/input ownership, app startup/idle cost, invalid user files and meaningful test assertions. Preserve existing widget slot row/col/span/overflow semantics for unrelated widgets. Defer optional performance work without observable user benefit.

## E. Technical strategy and dependencies

1. **Small domain types before GUI:** reusable calculation document/evaluator, structured date requests, diagram document/parser/serializer/renderer, regex visualization projection and Markdown block/export transformations should be pure/testable, with UI as a projection and explicit commands. Reuse exact existing domain engines instead of duplicating them.
2. **Explicit state and effects:** versioned document schema; source revisions; separate draft, last-good preview and saved baseline; file identity/external conflict before overwriting; atomic write paths; no side effects from layout, `search`, preview or background refresh. Source/presentation correlation must be monotonic so stale workers or old viewports cannot overwrite a newer edit.
3. **UI architecture:** prefer a native independent child viewport for Diagram Studio, following Regex's proven pattern; for other studios use an existing normal tool dialog or established native viewport pattern if justified. Keep every controls' focus, escape, scrolling and responsive layout reachable at small sizes; add Jump hints where the existing system can provide genuine visible-target coverage without introducing input-hook redesign.
4. **Use documented limits:** cap document size, parse complexity, rendered pixels and concurrent jobs in a user-explainable way. Reject oversized inputs before costly allocations; make work cancellable where it can outlive a frame. No automatic startup scans/loads of large documents or background continuous polling.
5. **Dependency order:** C01 independent; C02 independent; C03 independent; C04 is a dependency of C06's Mermaid rendering/handoff; C05 independent; C06 uses accepted C04 and existing Notes. Do not conflate categories through a premature shared framework.
6. **Dependency admission:** add packages only for demonstrated gaps (e.g. offline timezone rules or safe image encoding), lock versions, evaluate Rust/Windows build consequences and licensing. Do not pull down external scripts or embed remote content by default.

## I. Risks, bounded remediation and dependencies

| Risk | Mitigation/acceptance policy |
|---|---|
| Huge codebase, compile/test cost | Prefer testable domain changes; one scoped build at meaningful GUI boundaries; keep build duration and test runtime separately reported; do not repeatedly invalidate caches without need. |
| Native viewport not observable/owned | Reuse proven Regex Tester viewport lifecycle, test in real supported Windows environment; record failure honestly and stop bounded retries (generally initial + one cause-specific correction). Do not claim headless proof is native proof. |
| Mermaid text/data loss | Document supported subset, parse before modifying model, preserve unsupported draft, explicit source-preservation and roundtrip tests. |
| Diagram/regex visual performance | Bound graph sizes, cache on source revisions; keep expensive parsing/rasterizing out of idle frames. |
| Calculation errors or unit inconsistency | Use one authoritative conversion engine, reject non-finite and incompatible values, avoid evaluator side effects. |
| Date/time DST and relative-date surprises | Date/time reference snapshot; named timezone rules, disambiguate fold/gap, report exact date/offset. |
| Sensitive saved documents, HTML, SVG | Atomic writes, explicit export, escaping/sanitizing and bounded content; never execute untrusted Markdown/Mermaid content. |
| Notes and dashboard regressions | Preserve existing serde migration, note links, save/undo, action identities and Jump; run targeted old tests. |
| Category blocked partway through | Two focused remediation attempts at most per distinct confirmed failure boundary by default; document exact blocker and reject unsafe/unverified candidates. Proceed only to independent categories after committed clean handoff; don't conceal incomplete requested work. |

If a real feature-specific failure demonstrably requires slightly broader verification, record the rationale before expanding; no unbounded loops, app-wide architecture redesign or retries of historical unrelated remediation programs.

## J. Definition of Done

A category is complete only if (i) all its user-visible functions and edge cases work; (ii) the focused tests pass; (iii) native UI evidence exists when required or is **explicitly not verified** and completion is withheld; (iv) related existing behavior remains intact; (v) no known blocking defect remains; (vi) final diff shows only intended files; (vii) checkpoint commits/push results are recorded on the **correct child category branch**.

The overall Goal is **fully complete** only when all six categories pass, including the **independent Diagram Studio**, supported two-way Mermaid editing, Regex Visualize, Notes/Markdown parity, responsive Quick Tools and functional date/calc studios; required native evidence and targeted final first-party checks exist; and the **C06 `final_tip_sha`** correctly descends from C05 then C04, etc. No worktrees or intermediate merges. Otherwise report **partial delivery** with an exact per-category completed/blocked matrix—never imply the user has received an unfinished feature.
