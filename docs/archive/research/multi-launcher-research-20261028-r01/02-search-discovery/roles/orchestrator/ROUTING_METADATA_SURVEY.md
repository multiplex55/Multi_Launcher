## Question and result

Can existing declared prefixes alone establish complete discovery admission for an ordinary configuration? **No.** The inspected `reload_from_dirs` contains 81 unique builtin registration types. Of those, 37 override `query_prefixes` with a nonempty list; 44 inherit the trait's empty/global default. Snippets also overrides `always_search` to true despite declaring `cs`. Thus 45 registrations are manager-global under unrestricted provider policy and 36 are prefix-gated. This denominator is actual registration calls, distinct from the audit's 85 plugin-file roster; it does not correct or replace that file inventory.

The trait defaults and manager gate are visible in [Plugin contract](https://github.com/multiplex55/Multi_Launcher/blob/59156d96adcc73939c7171487a0cb582e3286587/src/plugin.rs#L112-L143) and [plugin_matches_search](https://github.com/multiplex55/Multi_Launcher/blob/59156d96adcc73939c7171487a0cb582e3286587/src/plugin.rs#L1411-L1437). The registration list is [reload_from_dirs](https://github.com/multiplex55/Multi_Launcher/blob/59156d96adcc73939c7171487a0cb582e3286587/src/plugin.rs#L876-L1008). [Settings::default](https://github.com/multiplex55/Multi_Launcher/blob/59156d96adcc73939c7171487a0cb582e3286587/src/settings/model.rs#L1136-L1150) supplies no enabled-provider allowlist or capability restriction (`None` for both). No user's settings or actual active roster was read, and this statement does not claim all registered services are live or all queries return actions.

Manager-global does not mean arbitrary grammar or unsafe implementation. Web Search and Calculator have source-reviewed restricted entry forms despite absent prefix metadata; see [their source](https://github.com/multiplex55/Multi_Launcher/blob/59156d96adcc73939c7171487a0cb582e3286587/src/plugins_builtin.rs#L10-L110). Snippets deliberately preserves adjacent `csfoo` via [always_search](https://github.com/multiplex55/Multi_Launcher/blob/59156d96adcc73939c7171487a0cb582e3286587/src/plugins/snippets.rs#L880-L890). A complete reserved-route manifest must account for those grammar distinctions, disabled known routes and actual origin/epoch/revision. The remaining global bodies were **not** classified by this survey. Empty metadata is not evidence they accept all natural language, and command labels are not proof of a complete grammar.

## Consequence for the proposed integration package

The versioned builtin coverage manifest must map these actual owners, record reviewed grammar scope and classify unresolved owners as Unknown. Known nonempty prefixes and `always_search=false` provide a manager-level head boundary; global/default/always-search owners require source-specific treatment. Do not turn this table directly into a Complete manifest. Dynamic/registered plugins and stale/unclassified metadata remain separately fail-closed under the proposal. Clarify whether Unknown coverage includes disabled owners so an allowlist example cannot silently evade reserved disabled syntax.

A synthetic Complete/empty-result context establishes only conditional ranker behavior. If a required unknown owner remains, the proposed global admission gate blocks all discovery queries in that configuration; report that usability cost instead of presenting synthetic success as default coverage. The future integration package must establish at least one real, explicitly bounded eligible configuration and decide default-like coverage before claiming user-visible acceptance. This is a precise amendment to the eventual integration work, not a new standalone recommendation, native experiment or production change.
