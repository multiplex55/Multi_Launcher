# Persistence and file safety — Goal 01 / M2-A

Source baseline: `59156d96adcc73939c7171487a0cb582e3286587`. Static source inspection only; no application, native test, filesystem experiment or user data access. This checkpoint deeply traces representative settings, Rename and Replace paths and targets adjacent recovery/automation/output owners. It does not claim exhaustive native or failure-branch coverage. Lifecycle admission/cancellation/retirement contracts are compared in [LIFECYCLE_AND_CONCURRENCY.md](LIFECYCLE_AND_CONCURRENCY.md).

## Settings transaction: draft to acknowledged runtime

The existing owner is `settings_save.rs`, not a missing global save coordinator. Editor Save validates its draft, validates radial settings against the published document, synchronizes plugin settings, merges File Search UI preferences, and constructs `SettingsSaveIntent::general(desired, baseline)`. The intent owns general fields plus only plugin keys changed relative to the editor baseline; plugin-selection intent owns only enabled plugins/capabilities. Invocation-related baseline fields are checked before preparation and again inside the persistence transaction. [S1], [S2]

The worker reads latest settings, overlays owned intent, validates Paste preferences, obtains a prepared runtime transition ticket, and waits for preparation. It then uses `Settings::update` to merge against **latest persisted settings under the process-local transaction lock**, not to serialize an old full editor snapshot blindly. The resulting committed settings are passed to `ticket.apply`; GUI drains terminal completion and applies accepted settings to live services. General live application publishes theme/resource policies/macro search settings and updates paths/capabilities/UI preferences through existing owners. This is a cross-owner protocol; atomic file rename alone cannot make runtime application transactional. [S3], [S4]

| Boundary / adverse sequence | Current guard and outcome | What static inspection does not prove |
|---|---|---|
| Two settings writers in this process | `SETTINGS_TRANSACTION` mutex serializes load-update-save; intent touches its owned fields. `update_checked` separately verifies inspected bytes and readback. | An in-process lock is not exclusion of an external process. The checked-byte API is not a property of every save call. |
| Editor was opened before invocation settings changed | Baseline validation runs before preparation and inside `Settings::update`; stale invocation assumptions reject rather than silently overwrite. | It does not make every arbitrary external JSON edit merge-safe. |
| Cancellation before persistence | Cancel ticket, resolve preparation/terminal authority; persisted file need not be rolled back if unchanged. | Native reconfiguration latency is not measured. |
| Persistence fails after preparation | Cancel prepared ticket and resolve whether runtime changed; report failure/reconciliation. | No blanket guarantee that arbitrary filesystem failures are recoverable. |
| Apply enqueue fails | Proven `NotEnqueued` permits cancelling dormant ticket and owned rollback. Already-enqueued status requires authoritative terminal reconciliation. | Transport timeout is not proof of “not applied”. |
| Runtime reply times out after persistence | Mark reconciliation required and continue waiting for authoritative terminal status; app keeps settings save pending. | There is deliberately no timeout-triggered blind rollback. Permanently stalled native service behavior remains a runtime question. |
| Later save changes owned fields before rollback | `rollback_owned` compares current values with this transaction's written values; preserve conflicts and report reconciliation instead of overwriting later changes. | External writer atomicity across this read/update protocol is not guaranteed. |
| Runtime applied but file was changed again | `finish_applied` reads latest and overlays acknowledged owned values for live application, warns about concurrent owned-field change; unrelated fields remain latest. | This report does not claim every persistence/live-state disagreement is impossible. |

These guards are source-backed in `run_settings_save`, `cancel_and_resolve`, `resolve_persisted_failure` and `rollback_after_failure`. The retry/reconciliation wait is a conservative correctness policy, not evidence of a current hang. Worker registry retains handles, stops admission and joins at final teardown; the per-app pending/reconciliation guard is separate from that registry. [S3], [S5]

Watcher reconciliation must be attributed to an actual owner. The inspected GUI installs domain watchers for actions, folders, bookmarks, clipboard, snippets, todos, favorites, notes and gestures; this trace found no generic settings-file watcher feeding `apply_saved_settings`. Explicit settings-editor load and save completion are established paths. Do not claim that every arbitrary external settings edit is automatically live-applied. JSON/domain watcher failure/reload contracts are reviewed separately below. [S6]

## Atomic file policy

`save_atomic` and `save_atomic_replaceable` intentionally differ. Both create a unique sibling with `create_new`, write and flush, close it and replace the destination; durable mode additionally calls `sync_all` and requests Windows write-through. Error paths attempt temporary-file cleanup. `backup_file` tries a unique hard link, then copy, and preserves collisions rather than overwriting an existing backup. These primitives provide a local single-file publication boundary; they are not a multi-store transaction or source-identity authorization system. [S7]

The Windows implementation uses `MoveFileExW` with `MOVEFILE_REPLACE_EXISTING` and, for durable policy, `MOVEFILE_WRITE_THROUGH`, plus bounded retries for selected transient sharing/access errors. The checked [official API evidence](roles/orchestrator/PLATFORM_EVIDENCE.md) supports those flags and their limits. It does not establish full power-loss durability for all filesystem/storage configurations or a multi-file atomic commit. Rename/Replace transactions below have separate native identity, scratch and journal authority; generic atomic JSON save must not be substituted for those owners. [S7]

## Catalog, backup, recovery and watcher authority

The application-data root and catalog establish store IDs, ownership and configured-path policy; they do not make every plugin store one transaction. Preload applies staged recovery before ordinary settings/plugins/watchers load, after single-instance ownership (startup trace in [SOURCE_MAP.md](SOURCE_MAP.md)). `RecoveryManager` refuses configured targets that cannot resolve to the same application-owned target from the settings-free bootstrap catalog. Grouped Macro/Radial document-plus-assets recovery cannot restore only one member. [P1]

Backup uses a reserved staging directory, per-store manifest, final rename, then recognized-snapshot retention. The manifest explicitly declares `PointInTimePerFileNotCrossStoreTransactional`. Retention keeps five recognized snapshots, validating product/version/ID, containment and reparse-free tree; unknown staging/unrecognized directories are not ordinary retention targets. Do not call the snapshot a cross-store instant or adopt the cleanup comment as proof of retained native file identity: inspected staging cleanup uses name/containment/reparse checks, unlike the handle-pinned Rename/Replace cleanup below. [P2]

Staged recovery records the selected candidate fingerprint. Startup reloads/version-checks the descriptor, reconstructs eligible candidates and compares fingerprints, materializes candidates before installation, verifies each installed destination, and clears pending recovery only after success. Group install preserves prior members and attempts rollback; incomplete rollback reports failures and preserved backups. This is deliberate recoverability with observable partial-failure handling, not an atomic multi-directory filesystem transaction. [P1], [P3]

DataService owns one worker with one pending slot, latest request per kind and bounded results. Same-kind requests coalesce; an active different StageRecovery refuses conflicting admission. Cancellation compares newest request ID. Shutdown closes admission, cancels active, clears pending and joins. The UI must distinguish staged-recovery completion from recovery already applied at startup. [P4]

JSON watchers retain subscription handles, share a per-path watcher, watch the **parent directory** for atomic replacement, and drop registration when the last callback disappears. Errors are logged rather than proving all future updates arrive. Target-repair `RepairWatchFence` atomically reserves exact paths, waits for admitted readers, defers/coalesces callbacks, and leaves paths blocked if an initiated transaction is dropped without verified resolution. This is a specialized existing multi-store publication owner; do not replace it with arbitrary event suppression or assume every file reader participates. [P5]

## Batch Rename: verified preview through journaled moves

The UI freezes only a Ready `VerifiedRenamePreview` with a nonempty verified plan after confirmation. The scanner/coordinator receives the typed `VerifiedRenamePlan`; the transaction layer cannot create authority from a display filename alone. `execute_apply` refuses unresolved prior recovery, prepares **all selected native file guards before mutation**, and persists the receipt before the first move. [N1]

Native admission checks the opaque evidence matches the selected source, root identity, canonical source/parent path, same-parent target, regular non-reparse source, native file ID, length and modification time. It rejects duplicate native identities and imposes per-file/batch hash limits, computes content SHA-256 from the held source and preflights destinations. Guards retain source and verified directory handles. The operation is not an arbitrary cross-directory move. [N2]

| Transition | Durable authority / native operation | Refusal, cancellation or interruption |
|---|---|---|
| Prepare | Root/parent/source evidence and handles, target preflight, initial journal save | Any guard failure or initial save failure returns without requested file changes. |
| Original → reserved stage | Record stage candidates and `pending_move` including file identity/hash **before** move; rename held file without replacement; verify; update current path/outcome and journal | Collision retries only a new owned stage. Uncertain post-move state retains pending intent rather than guessing. |
| Stage → final target | Record pending move; no-replace rename; post-verify; record publication | Destination occupant is not intentionally overwritten. Failed verification/receipt persistence becomes recovery, not a success toast. |
| Cancel after partial apply | Transaction rollback uses retained verified guards; journal describes remaining state | Cancellation is not all-or-nothing magic. Failed/uncertain compensation is retained for explicit recovery. |
| Undo / interrupted startup inspection | Load/validate/reconcile recorded receipt; verify recorded candidate roles by root/parent/file identity, length/modification/hash; prepare guarded undo; journal Undoing before moves | Zero/multiple matching roles, changed payload/identity or occupied target refuse an unsafe guess; unresolved prior receipt blocks a fresh apply. |

This trace read apply, staged/published move transitions, undo admission and recorded-role reconciliation; it did not inspect every rollback permutation. Exact owners are `batch_rename_transaction.rs::{execute_apply, execute_undo, stage_entry, publish_entry, reconcile_receipt}` and `file_operations.rs::{prepare_guarded_rename_batch_native, GuardedRenameFile}`. [N1]–[N4]

The native rename helper calls `SetFileInformationByHandle(FileRenameInfo)` on the held **source**, sets `ReplaceIfExists = false`, and builds the absolute destination from a validated single leaf and retained parent's canonical path. `RootDirectory` is null; the source comment records a fixture-specific relative-handle limitation. Consequently this report does not describe a destination-relative `RootDirectory` atomic guarantee or reproduce that fixture. Directory-handle protection, filesystem semantics and adverse native interleavings require later focused proof if disputed. No current defect follows merely from the null field. [N5]

## Replace: exact approved bytes, original backup and publication recovery

`ConfirmedReplacementRequest::confirm` requires completed discovery, Ready candidate, explicit nonempty/unique selection, per-file readiness/membership, original snapshot length/hash, changed output bytes/hash, replacement revision, bounds and opaque native scan evidence. GUI confirmation returns a revision-tagged typed request to its owner; the displayed diff is not reconstructed into a different mutation at execution time. [X1]

`apply_one_file` reopens/adopts guarded source proof against root/file/parent identity, original length/modification/hash and original bytes. Changed root/parent/source yields a skip/refusal. It persists BackupPending, creates and verifies original recovery payload, records backup identity, then creates a `CREATE_NEW` sibling containing the **exact approved output** and verifies/flushed output. Before any relocation, the journal names the backup/output identities and phases. [X2]

It next journals OriginalMovePending, moves the held original to its owned sibling and records that identity. It journals PublishPending, publishes output with no replacement of an unexpected occupant, and verifies output at the chosen original path. The durable Applied receipt precedes identity-pinned deletion of the original sibling. Cleanup failure retains the stage and message; it does not turn an unknown occupant into deletable garbage. [X3]

Representative boundaries:

- **Cancel before original move:** remove only the verified output stage; save Cancelled or RecoveryRequired according to cleanup/receipt result. The original has not been intentionally relocated.
- **Cancel between original move and publication:** guarded compensation attempts original restoration; outcome remains journaled and uncertainty is not hidden.
- **Another occupant appears before publication:** no-replace publication refuses; compensation may also fail if its target is now occupied, so recovery remains necessary. Do not report this as a guaranteed transparent rollback.
- **Published output exists but final receipt save fails:** return recovery-required; do not repeat the whole replacement under assumed absence of effects.
- **Restart after interruption:** inspect recorded backup and exact output/original roles. A verified output at the selected path can reconcile Applied; a verified unchanged original can reconcile no mutation. Cleanup of original sibling requires its recorded identity/hash plus a guarded file owner, never filename prefix alone. [X2]–[X4]

Restore/undo uses the same receipt roles and verified backup identity. The deep trace here covers representative interrupted-apply recognition and owned-stage cleanup; the full interrupted-restore matrix and native crash/power-loss behavior are **not verified**. Current code already contains these protocols at the pinned master; no historical Goal 09/12 failure report was adopted as a current bug.

## Diff folder mutations have a different guarantee

Diff copy/delete plans retain exact selected paths, roots, expected source/destination state and generation. The GUI consumes its confirmed preview object, captures dirty document paths at execution, and permits recycle deletion only. Executor rechecks containment, root/path meaning, metadata and dirty destination/descendant protection. Recycle failure has no permanent-delete fallback; `spawn_recycle_delete` rejects a permanent plan. These are meaningful counterguards. [D1], [D2]

They are **path-based** mutations after those checks: copy calls `fs::copy`; delete calls the trash backend. On Windows `FileIdentity` is kind/length/modified, with no native volume/file ID fields (device/inode are Unix-only); non-Unix root comparison checks canonical path. Thus a same-metadata replacement or replacement between validation and mutation is not excluded by this owner. Rename/Replace's native-handle proof must not be attributed to Diff by shared naming. [D1]

[AUD-002](findings/AUD-002-diff-mutation-identity.md) records this as an **unaccepted candidate for M2-B**, with high confidence in the source distinction and unverified native likelihood/consequence. No broad native migration is accepted. Minimum future proof must first choose the intended concurrent-writer contract, model a deterministic validation/mutation interleave and compare a focused existing-owner repair against no change. Ordinary copy/delete behavior and user confirmation must remain intact.

## Automation authority, nested execution and receipts

Hot Folder notifications are settled candidates, not authority to execute any matching string. Ready lease transfer checks exact service/lease, current rule enabled state/fingerprint, capability support, first matching rule, native watched root and fresh source evidence; control gates/rate limits/processed keys/causal outputs suppress stale, duplicate and feedback-loop work. Intent journaling and an actual terminal receipt are separate from merely acquiring a ready candidate. Pause closes admission and cancels active operation; rule changes cancel an active changed/disabled rule. Resuming uses the current gate epoch. [H1]

Registered launcher actions require exact unique persisted target/fingerprint, selected Universal Action availability, allowed result execution and a supported external process target. UI intents, arbitrary namespace commands/URLs and unavailable adapters are refused. The GUI adapter remains the existing typed-command/runtime bridge from M1-B, not a generic confirmation bypass. [H2]

Macro eligibility compiles/fingerprints the dependency program and validates unattended defaults; it inspects **enabled instructions across every dependency**, not only the root. Variable/control/notification/delay/sound/Call/Return operations and supported variable conditions are permitted; clipboard text actions and interactive/unsupported instructions are refused. Nonwaiting process actions require strong enable confirmation. A root macro that delegates to an interactive/clipboard child is not made unattended merely by its root type. Nested runtime execution uses the same admitted root/control/input owner, bounded frames and transition budget ([lifecycle report](LIFECYCLE_AND_CONCURRENCY.md)). [H2]

The Hot Folder journal has explicit byte/row/pending/counter limits; in-memory receipts, processed identities and causal output collections are bounded. Receipts include source/output **paths**, native identities/length/time/hash, rule/target/fingerprint, status/phase and safe bounded reason; arguments and macro bodies are intentionally absent from the external-target receipt. “Metadata” therefore does not mean privacy-free. Durable receipt failure trips/reports state rather than retroactively proving the action never happened. [H1]

## Clipboard, Paste and output ownership

Three separate contracts must remain distinct:

| Owner | Publication / external-change contract | Retained data |
|---|---|---|
| Clipboard history plugin | Reads system text only on its synchronization path; process-local transaction reloads persisted history, mutates and saves replaceably before version bump/memory publication. Same captured-snapshot APIs compare full history for conditional edits. | Raw clipboard strings, bounded by configured entry count (default 20; settings UI 1–200), persisted to clipboard history. Count is not a byte/privacy bound. Tests disable OS synchronization and seed only synthetic history. [C1] |
| Clipboard Modify dialog/service | Dialog commit compares current clipboard bytes to captured baseline unless user confirms conflict; confirmed commit rereads current for undo original. Service serializes its commits, writes output, then publishes one undo record. Undo deliberately writes recorded original even if an external copy occurred; existing test states this policy. | Original/modified raw text plus operation label in the service undo record; preview holds full output separately from display truncation. No claim this undo is an ownership-preserving external clipboard lease. [C2] |
| Clipboard Modify immediate operation | Worker reads, transforms and commits; one metadata-pending operation per coordinator. Clearing metadata does not cancel its private token or undo effects. Actual production `cancel_pending` caller found is app `on_exit`, so normal close/restart overlap is not established. | Detached worker text until return; accepted completion metadata drives success hook. **NO_ACTION** for a speculative cancel redesign from its name alone. [C3] |
| Paste Sequences | Each step explicitly publishes text under a native clipboard-open guard, then rechecks lease/focus before input. Completion/cancel does not restore an old clipboard snapshot; final text remains for a normal OS paste, and later external text is not restored over during cleanup. | Run owns rendered step strings, exact external target and input lease; source publication epochs invalidate admission. This is an input-authority lease, not a promise to suppress external clipboard edits between intentional steps. [C4] |

The Macro document source-publication fences installed in `main.rs` participate in Paste admission. They prevent admitting against an inconsistent source publication; they do not make all OS clipboard writers participants in a transaction. Native clipboard busy/input/hook timing remains untested. Do not add synthetic input/delays or a second hook based on source-only speculation. [C4]

## Capture, editors and read-heavy utility outputs

Screenshot owner accepts current joined completion, then the command host delivers the owned image to clipboard/editor and applies command outcome/history only for completed delivery. Editor Save applies current edits and writes an image to the chosen path; Copy sends edited pixels to clipboard. The inspected editor save uses `img.save(path)` and is not the atomic JSON or native recovery transaction. Cancellation before authoritative completion must not create a late editor/history item. QA framebuffer export branches are feature-gated diagnostic behavior, not the normal save flow. [O1]

OCR capture/recognition owns transient pixels/document until completion; the view accepts generation/current presentation authority, and Copy writes **current edited result text only on explicit Copy**. Mere rendering/progress does not read/write clipboard. Shutdown cancels/releases selection/parking/view without waiting for detached worker join. Pinboard pending/live sessions own capture bindings, first-frame gate, frame leases and shared CPU/GPU reservations; close can retain retired worker handles and frame leases until consumers release them. Neither visible closure nor cancellation proves immediate memory/native release. [O2], lifecycle report.

| Read-heavy utility | Inspected session/result/output boundary | Coverage limit |
|---|---|---|
| Hash Generator | Dialog retains cancelled `HashJob` until terminal event and refuses a new job while it exists; generation/request ID rejects stale presentation. Worker cooperates between reads and publishes one terminal event; no join receipt. Digest Copy is explicit. | Targeted dialog/job owner and representative cancellation; no disk-throughput/OS read-latency measurement or every hash algorithm audit. [U1] |
| JSON utility | One dialog-owned shared worker state, one coalesced pending build and completion; generation/revision gates publication. Drop sets shutdown, clears pending/completion and wakes worker; spawn does not retain JoinHandle. Tree snapshot Arc and output authority are distinct from a background build. | Targeted tree projection owner, not every JSONPath/transformation/render/export path. No hard interruption of an active pure build established. [U2] |
| Regex Tester | Caller-clock debounce and revision invalidation; synchronous evaluation with explicit input/capture/match/materialized/output/test-case limits. Borrowed evaluated text applies only to exact source/revision. Pattern/flags history is capped at 50 and omits test text/replacement; explicit presets may store sample/replacement. | Targeted scheduling/policy/retention; no measured frame-time or full Rust regex/explanation audit. Existing bounds are not benchmark results. [U3] |
| Table/XML/Diff/Duplicate/Image | Owner-specific source/revision/native evidence and resource/session lifetimes are covered in lifecycle comparison and representative file flows above. Table export basis and resource-owned receipt prevent confusing dirty/current and previous-valid output. | Deep representative ownership, targeted remaining algorithms; not a blanket claim that all parsers/decoders/schema/native backends or exports are safe. |

Pure color/date/unit/text/QR computations, bulk presentation, graph/note-link transforms, archive traversal, and full multi-manager/window persistence remain surveyed unless explicitly cited in the coverage matrix. No new change is recommended from those surveyed bodies. Their shared app dependencies do not by themselves justify a larger audit or execution campaign.

## Concern disposition and minimum future proof

| Concern | Mechanism and counterevidence | Confidence / disposition |
|---|---|---|
| “Cancelled search means no worker remains” | Current File Search ID fencing protects results; cancellation event is early; backend ripgrep kill/wait cooperates. Other owners retain/join/reap explicitly. | High source confidence; native wait/cumulative resource cost unknown. Unaccepted candidate only if a concrete resource complaint or required bound warrants future stalled-backend proof. |
| “Settings timeout must roll back” | Enqueued runtime apply may have happened; authoritative ticket reconciliation and owned rollback already exist. | High source confidence. **NO_ACTION** for generic save-coordinator replacement; preserve protocol. |
| “Rename/Replace have no recovery boundary” | Verified evidence, held handles, journal-before/after moves, exact stage roles/backup identity, no-replace publication and guarded cleanup are current. | High source confidence for named paths, runtime crash/durability unverified. **NO_ACTION** for adopting historical reports as current bugs or replacing these owners wholesale. |
| Diff concurrent replacement identity | Metadata/path checks precede path-based mutations; Windows FileIdentity omits native file ID. Confirmation/dirty/recycle-only/containment guards remain. | High source distinction; native failure not reproduced. **AUD-002 unaccepted**, M2-B decides contract and scope before any pair/fix. |
| Generic snapshot “transactionality” | Backup manifest declares per-file consistency; grouped recovery has materialize/verify/rollback/error paths. | High source confidence. Preserve documented distinction; no cross-store-atomic guarantee or generic framework action. |
| Clipboard cancellation name implies effect rollback | Immediate operation locally owns token; metadata clear caller is shutdown. Paste and dialog/undo have separate explicit publication semantics. | High source confidence. **NO_ACTION** for hypothetical restart race; do not alter undo/publication policy without product need. |
| Summary/history privacy | Macro summary safe metadata budgets differ from clipboard raw text, explicit regex presets, file receipts and capture outputs. | Source-backed data classes, no user-data inspection. Future search must not ingest retained raw content by assuming every history is safe metadata. No new privacy feature accepted here. |

Only the existing AUD-001 recommendation remains accepted for future review. AUD-002 and runtime resource questions are not an implementation backlog and have no unapproved pseudo-goals. M2-B must reject, narrow or accept/package them. Required future app tests, if later authorized, must disable Paste next/cancel shortcuts before construction. Existing watcher/clipboard/Macro/XML/Diff/File Search tests were inspected as source (some are model-only/native-gated); no passing result is claimed.
