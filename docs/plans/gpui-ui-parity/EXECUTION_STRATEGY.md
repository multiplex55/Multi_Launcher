# GPUI migration execution strategy

Read and follow this strategy before planning, implementing, reviewing, verifying, or resuming any GPUI migration work. It governs infrastructure priorities, implementation and verification scheduling, batching, and build efficiency. The [Master Goal](../../CODEX_GOAL_GPUI_UI_PARITY.md) defines the objectives, full functional scope, and final acceptance. The [Kickstart](../../CODEX_KICKSTART_GPUI_UI_PARITY.md) defines initialization, resumption, and coordination. Repository [AGENTS.md](../../../AGENTS.md), nested instructions, and the current agent configuration govern repository engineering and agent conventions. Use the [Validation Strategy](VALIDATION_STRATEGY.md) for evidence design and record results in the [checkpoint ledger](CHECKPOINTS.md).

## Prioritize infrastructure and broader coverage

Address foundational blockers and reuse existing abstractions before extracting common infrastructure. Use Hash Generator and the implemented launcher and utility interfaces as references. Prioritize broadly applicable capabilities according to real dependencies.

- Global hotkeys, visibility, foreground restoration, virtual desktops, native placement, and window lifecycle.
- Shared docked, popout, pinned, independent, and retained utility hosting.
- Keyboard navigation, focus, Escape, Jump Mode, accessibility semantics, and native interaction patterns.
- GPUI Kit components, layout, typography, sizing, styling, editors, tables, virtualized lists, filters, menus, dialogs, and confirmations.
- Typed command dispatch, plugin admission, result activation, and universal actions.
- Canonical Settings ownership, checked persistence, and preservation of unrelated data.
- Background ownership, cancellation, progress, retirement, and Activity Center integration.

Extract abstractions for actual consumers or established requirements. Keep substantial features in their own modules with retained views and clear ownership. Use the main frontend for application coordination. Large GPUI render trees have caused native stack overflows. Address that pressure through independently rendered components and child views while preserving the normal main-thread stack size.

For each new GUI family, identify which retained hosts, Kit editors, tables and virtual lists, selection and filtering controls, pickers, clipboard effects, checked writers, confirmations, previews, progress and cancellation, keyboard and Jump Mode routes, accessibility semantics, and window focus and geometry services already meet its needs. Share new infrastructure when concrete consumers establish its ownership and contract. Keep plugin-specific views focused on behavior unique to the feature.

Fix cross-cutting defects at the responsible boundary. Distinguish work that blocks implementation, cross-family regressions, isolated plugin defects, minor presentation work, environment-limited evidence, and deferred acceptance criteria. Give each deferred criterion an owner, explicit acceptance conditions, and a scheduled verification stage. Continue safe independent work while isolated or environment-dependent work waits. Group small control or appearance refinements after broader implementation when safe.

## Select coherent GUI batches

The Planner selects related work by dependencies, shared infrastructure, and concrete reuse. A typical batch is three to five smaller surfaces or several meaningful increments of a substantial family. Adjust scope for complexity, safety, and link cost. Use G00–G26 and the existing packets as the coverage and ownership ledger. Document dependencies and GUI ownership when scheduling independent work out of register order.

Examples include structured text with JSON, XML, and Regex. Clipboard History, Clipboard Modify, and Clipboard Snippets share clipboard workflows. File Search, Folder Size, File Locks, Duplicate Finder, and ZIP utilities share file operations. Diff, Batch Rename, and Search & Replace can share preview and apply controls. Notes and Markdown Studio share document workflows. Calculation Pad, converters, and table tools share input and data presentation. Dashboard and organizer widgets, screenshot and native overlays, and Automation, MkMacro, Radial Menu, and related authoring interfaces offer further families. Choose concrete batches from the source and documented dependencies.

## Schedule around compilation boundaries

Recent shared-library and launcher test builds have taken 12–30 minutes. Warm launcher-only test builds can take about 15–30 seconds. The Planner should use the actual affected packages and targets to order several related checkpoints where practical. Identify their shared-engine needs together, consolidate related library changes, and establish stable interfaces before multiple frontend consumers depend on them. Check those interfaces during development and verify high-risk shared boundaries before substantial dependent implementation. Keep frontend-only work within frontend targets when the existing ownership fits. Preserve one authoritative implementation and choose the architectural boundary on its merits.

Keep small, coherent commits. Related lower-risk increments may be compilation-checked and committed before one grouped linked verification run. Aim for two to five related increments between expensive shared-library builds when their dependencies, risk, complexity and verification backlog allow it. Run inexpensive launcher-only tests more frequently when they provide useful evidence. Apply the immediate verification requirements below at high-risk boundaries and record the outstanding checks for each unverified commit.

## Pass 1 · Functional implementation and coverage

Inspect the relevant egui implementation and map its real controls, modes, state, actions, and effects. Implement usable GPUI workflows using the authoritative engine, commands, canonical data, and persistence. Each shipped increment must exercise its actual feature. Count empty shells, mock data, and nonfunctional controls as unfinished.

Write meaningful tests alongside the implementation. Use scoped `cargo check --locked --profile fast-dev --bin multi_launcher` and include affected library or test targets when appropriate. Check meaningful test code before the linked batch when practical. Use these checks for types, ownership, API and integration issues. Obtain independent source review and resolve blocking architecture, safety, and compatibility issues during the increment. Record tests as written, type-checked, or executed according to the actual evidence.

Use one active source writer and keep small coherent checkpoint commits. Safe independent implementation can proceed with explicit verification gaps. Maintain separate functional and acceptance status for every GUI.

## Pass 2 · Grouped verification, refinement, and acceptance

Before an expensive link, identify the affected Cargo packages and targets. Use scoped locked application, library and test-target checks where practical. Inspect test-only imports, feature gates, macros and fixture setup. Verify the intended selectors from the test inventory and confirm the run selects a nonzero intended set. Compile only affected test targets. Continue using Nextest and the repository runner configuration.

Combine focused Nextest selectors by affected package and target. Reuse linked binaries for additional selectors and failed-test retries while the relevant source, dependencies, build configuration and fixtures still apply. Count results only for the source those binaries cover. Record compilation, linking, and execution costs separately where evidence distinguishes them. Some focused links have taken 20–30 minutes while tests run in seconds. Favor meaningful implementation between those builds and preserve compiler flags, profiles, features, toolchain, environment, target directory, and caches unless the work needs a change. Full-suite testing and release builds require a concrete scope, risk, or existing acceptance gate.

While a long compile or link is active, use the Planner, Reviewer and parent for independent read-only discovery, next-batch planning, review of committed source, and reusable component discovery. Prepare owned fixtures, native scenarios, selectors and relevant records. Keep source inputs to the active build stable and reserve the target directory for one expensive Cargo process at a time. The single writer and parent build ownership still apply.

Where practical, build one native Windows application candidate for the batch and exercise the related workflows in egui and GPUI using that same artifact. Compare behavior and appearance against recorded baseline outcomes. Collect related failures before building a correction if that is safe and leaves the cause clear. Combine related fixes and cosmetic adjustments into scoped correction cycles and revalidate the affected behavior. Verify each batch before allowing excessive unverified implementation to accumulate. Formally accept only the criteria whose required evidence has passed.

Parameterize recurring Windows scenarios by GUI, typed entry route, fixture and expected effects. Reuse the steps for Search open, keyboard and pointer activation, Dock and Pop Out, saved geometry, pinning, focus and foreground transfer, Escape and Close, Jump Mode, clipboard interaction, persistence, cancellation and hidden-root behavior. Exercise applicable scenarios across related workspaces with the same candidate. Keep automated state and engine results separate from Windows interaction evidence. When desktop access is unavailable, continue eligible work and keep a bounded replay queue with the next native batch and outstanding risks visible in the checkpoint records.

## Investigate build performance at an existing checkpoint

Start with existing receipts and Cargo timing reports. Capture timings on the next already-required representative build where practical. Inspect the effective compiler and linker settings, shared-crate compilation and code generation, debug information and link time, CPU use, peak memory and paging, parallelism, incremental behavior, target storage and expensive dependency or crate boundaries. Distinguish measured costs from unknowns, including when Cargo reports an aggregate compiler invocation without separating linking.

Use that evidence to assess the current `fast-dev` profile, debug information level, Windows linker, job count, incremental compilation, compiler caching and selective crate extraction. Keep this investigation bounded to the migration checkpoint. Preserve the existing configuration and cache while evaluating options. If an option has a credible measurable benefit, compare one controlled change at a time using representative incremental work and retain the established configuration as a fallback. Adopt an adjustment only when the evidence shows a meaningful gain while preserving behavior, debugging, compatibility and verification. A broad build redesign or workspace restructure requires a concrete reason beyond speculative speedup.

The combined Folder Size report-effects test build took 1,500.2 s, with 815 fresh units and three dirty units. The shared-library test unit took 1,498.8 s, the regular library unit took 1,186.2 s with 861.2 s attributed to the compiler frontend, and the launcher test unit took 144.8 s. These units overlapped with two jobs on the eight-logical-CPU Windows MSVC host. The subsequent File Lock host build reused 816 units and compiled only the launcher test unit in 22.6 s, with 24.0 s elapsed. The cache resides on fixed NTFS storage. `fast-dev` inherits `dev`, uses line tables for workspace code and disables debug information for dependencies. Cargo reports aggregate test-unit time here, so linker invocation, standalone linker time, peak memory, paging, and active CPU utilization remain unmeasured. Retain the profile, job limit, and warm cache for now. The measured cost supports batching shared-library work and keeping GPUI-only edits in the launcher target. ## Record progress and coordinate ownership

Keep the existing goal, checkpoint, validation, and parity documents current at meaningful boundaries. Distinguish specified, implemented, compilation checked, awaiting grouped verification, automated tests passed, native verification passed, formally accepted, and blocked or deferred. Record the GUI surfaces and working flows delivered, shared infrastructure reused or introduced, expensive shared-library build and launcher-only build counts, corrective builds, compile and link time, test execution time, outstanding native replay and opportunities for the next batch. The Planner identifies the real source owner, related checkpoints, high-leverage infrastructure, batch sizes and targeted evidence. The Implementer delivers coherent functionality and reusable components, preserves compatibility, writes focused tests, and keeps changes buildable with inexpensive checks. The Reviewer examines coherent changes together and reviews high-risk boundaries immediately. Assess ownership, behavior, safety and regression risk, and distinguish blocking fixes from work for grouped refinement. Reuse earlier discovery and verified evidence. Handoffs should give the objective, relevant paths, shared contracts, outstanding work, known risks and required checks. The parent coordinates one source writer, Cargo and desktop ownership, evidence, commits, and best-effort pushes. Read-only work may run independently. Continue resolving foundational defects and delivering related GUI families until the original parity goal is complete or every remaining path has a genuine recorded blocker. Keep testing throughout implementation and require the original functional, safety and final acceptance evidence.
