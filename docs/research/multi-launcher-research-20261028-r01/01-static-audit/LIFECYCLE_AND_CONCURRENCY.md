# Lifecycle and concurrency — Goal 01 / M2-A

Source baseline: `59156d96adcc73939c7171487a0cb582e3286587`. This is static research, with bounded deep traces of replacement/close/reopen and targeted review of the other owners below. No application, native API, build, test or benchmark was executed. Source mechanisms are not latency measurements or proof that an operating-system call always returns.

## Distinctions that callers must preserve

There are four different events: a request loses authority; cancellation is requested; a terminal result is published; the executing worker and its resources retire. The code already models these separately in several places. `ActivityRetirement::{Pending, Confirmed, Unavailable}` and `ActivityTask::finish`/`retirement_confirmed` expose the distinction; Activity UI is an observer and cancel-capability consumer. It does not own the underlying operation. [A1]

The shared thread reaper reserves capacity before ownership transfer. Its normal supervisor invokes the callback **after `JoinHandle::join`**, outside the reaper lock. A completion notifier signals that user work has returned, then the supervisor joins the OS thread. Supervisor-start failure has an explicit detached/error path; a transfer request is not itself proof of a successful join. Keep owner-specific error handling and do not relabel a transferred or cancelled operation as already retired. [A2]

## Owner comparison

“One pending” describes the owner's mailbox, not a bound on all workers ever started elsewhere. “Unavailable” means the inspected owner supplies no retirement receipt; it is not a claim of a leak. Admission is local unless stated otherwise.

## Representative adverse sequences and counterguards

1. **Search A is slow; user starts B, then A completes.** Indexing rejects A by generation/config and cancellation under the publication lock. File Search rejects A by SearchId during drain. Both protect visible state. File Search's local Cancelled event can be consumed before A's backend returns; ripgrep kill/wait is concrete backend counterevidence against a claim that “cancel does nothing”. Cooperative native directory or OS reads may still have nonzero/unbounded external wait. No resource leak or UI freeze was reproduced. [L1], [L2]

2. **Close utility, immediately reopen while old work is blocked.** Duplicate Finder refuses until actual-join receipt. Image Compare refuses until worker-local resource teardown signal and keeps one shared budget. XML retains Closing and polls join. Table advances lifetime and cancels while retaining its one worker, then joins only at shutdown. These are different intentional contracts; standardizing their names is less important than preserving admission/resource authority. [L6]–[L9]

3. **Rescan folder comparison while refinement threads run.** `prepare_rescan` invalidates generation and clears local queue/in-flight tracking; completed old results are fenced by roots/rules/metadata. Current local `MAX_IN_FLIGHT` is therefore not proof of a process-wide bound across repeated rescans. Inspecting blocked-read cost and repeated-rescan admission would be the minimum future proof if a resource complaint exists. It is an unaccepted investigative candidate, not an established defect. [L4]

4. **Cancellation occurs between clipboard publication and input injection.** Paste performs lease/foreground checks at multiple effect boundaries, including after publication. It can terminate without injecting the paste; cleanup must respect its publication ownership and preserve external changes. Clipboard Modify immediate execution has a different explicit contract: clearing pending UI metadata cannot undo a side effect already performed by the detached worker. Do not transfer Paste's cancellation guarantee to that class. [L11], [L12]

5. **Old macro stop arrives after a new run is admitted.** Run-specific stop compares ID under the admission lock. Queued control commands are ignored on the worker because they were already applied synchronously. Nested calls have one root admission and control/checkpoint/input ownership. Replacing this with per-action/background workers would lose existing stop ordering. [L13]

6. **Screenshot/OCR worker publishes while UI shuts down.** Screenshot result delivery waits for joined worker and current generation; shutdown transfers worker ownership. OCR keeps terminal acknowledgement for ordinary cancellation but intentionally releases receiver and UI authority during app shutdown. Neither code path should claim that closing a viewport proves a native capture/OCR call returned. [L15], [L16]

## Retention and read-heavy outputs

Table export receipts are resource-owned payloads with exact lifetime/document/source/view/selection/options guards. “PreviousValid” export is an explicit basis distinct from current dirty input; retaining it is not automatically stale-result corruption. XML snapshots are Arc-published session outputs scoped by source/document revision; the closing session remains the engine/thread owner. Image Compare and live pins similarly make snapshots/frame leases part of the budget lifetime. UI state reset does not force every downstream Arc/lease to disappear. These are existing ownership patterns to preserve. [L6], [L7], [L9], [L17]

Macro summaries retain metadata in memory under explicit count/byte/row budgets: 100 completed runs, 4 MiB charged metadata, 1,024 step aggregates per run, bounded/truncated macro name, safe failure location, category/counter/timing totals. The summary type has no arbitrary variable-value, clipboard-body, OCR-text or captured-frame payload field. Full runtime snapshots/debug/recording/store data are different classes and this statement does not describe their retention. No persisted summary writer was established by the inspected `SummaryHistory` owner. [R1]

## Tests inspected and limits

Static inspection reached existing tests for cancelled/stale File Search state, reaper capacity/completion/failed-supervisor behavior, folder-generation acceptance, export receipt keys, XML closing/reap, blocked screenshot shutdown, OCR late-publication isolation, macro run-specific stop/nested frame limits and pin cleanup. Test bodies/assertions are design evidence, **not passing results**. This checkpoint does not claim every backend, native cleanup branch, worker panic or full shutdown permutation was inspected.

The minimum future proof should follow the owner: deterministic stalled backend plus replacement and completion barriers for admission/authority; join/cleanup receipt for retirement; a small native smoke only for the specific API whose blocking/teardown behavior matters. App fixtures must set Paste Sequences `next_hotkey = None` and `cancel_hotkey = None` before construction, preserving production defaults. No broad test campaign or common worker-framework recommendation is accepted by this report.
