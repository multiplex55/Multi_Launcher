## 1. What approval currently means

`DiffDialogState::plan_mutation` selects entries present on the requested source side, uses the correct left/right roots, captures the runtime generation, and stores a nonpersisted `OperationPreview` containing the plan. It refuses another mutation while the runtime is active. Copy preview identifies direction, paths, overwrites, conflicts and errors. Delete preview says “Delete … (Recycle Bin)” and “move to Recycle Bin.” Fatal planning errors, a dirty-path planning error, and an active operation disable Execute. [S2:1018–1126; S3:22–132]

On Execute, `show_operation_preview` takes that same plan and a newly collected dirty-path set into `spawn_copy` or `spawn_recycle_delete`. This preserves preview intent; it does not freeze external writers or subsequent editor changes. Runtime identity/generation is a UI lifecycle boundary, not a filesystem lock. [S2:1129–1178; S4:148–160,288–320]

There is no inspected statement of a required concurrency guarantee such as “only the exact object approved can ever be changed.” Approval of this research package does not supply that requirement. Conversely, categorical Recycle Bin preview text is not proof that every Windows Shell target can actually be recycled. M2 must keep that distinction visible rather than silently treating current wording as a proven native guarantee.

| Concept | Current representation or observation | What it does not establish |
|---|---|---|
| Metadata equality | `FileIdentity`: kind, length, optional modification time; additionally device/inode on Unix | Equal bytes; Windows object identity; effect-time stability |
| Object identity | Diff has Unix device/inode fields; selected native Rename owner uses volume serial + 128-bit file ID | Immutable content, globally durable identity, ownership of a different destination |
| Content identity | Diff mutation planning/execution does not capture a content digest | A digest would still require protected reads and binding to the later effect; it alone would not authorize destination replacement |
| Path containment | Relative-component checks; canonicalized nearest existing ancestor under captured canonical root | A held ancestor chain or immunity to replacement after the check |
| Mutation authority | User approves captured paths/overwrite state; executor later resolves those paths | An OS capability binding each effect to the approved source, destination and parents |

`FileIdentity::read` rejects a direct symlink. That is not an all-reparse-point native audit. Non-Unix `same_root_identity` reads a directory then compares canonical path spelling; Unix compares captured device/inode. Do not summarize either as a universal native object lock. [S1:30–65,137–207,540–553]

One source nuance matters to C1: execution uses `FileIdentity::read(&dst).ok()`, so **all** destination identity-read errors collapse to `None`, unlike planning's explicit `NotFound` admission. Thus the execution observation is not even a proof of absence for every error case. This is recorded as a limitation in this owner; it is not repaired or promoted into a separate audit here. For C2, the same `None` differs from an expected `Some`, so it refuses the overwrite. [S1:430–479,525–528]

## 3. Responsibility and lifetime map

| Object/state | Current owner and lifetime | Required distinction |
|---|---|---|
| Selected roots and relative paths | `CopyPlan`/`DeletePlan`, from preview through worker | Captured canonical strings and metadata; no root handles in these plans |
| Ancestors | `ensure_contained` observes nearest existing ancestor while checking | Observation ends before effect; lexical target equality is not ancestor identity |
| Source file | `PlannedCopy.expected_source`; read again in `fresh`; `fs::copy` opens by path | No retained approved source handle and no frozen bytes |
| Destination file/absence | `expected_destination: Option<FileIdentity>` and `overwrite` | `None` and approved `Some` are different authority, even though they call the same overwrite-capable API |
| Recursive descendants | Snapshot walk for copy; selected directory item for recycle | A directory metadata check is not authorization/revalidation for every changing child |
| Dirty editor state | GUI `dirty_paths` at preview and again at dispatch; immutable worker set | Blocks known dirty targets and their destructive ancestors; not an ongoing editor lock or external writer exclusion |
| In-flight effect and results | Worker, `ExecutionReport`, channel; active runtime handle owns receiver/cancel flag | A cancellation request can coexist with an effect already executing; generation filtering only decides whether GUI accepts a report |
| Scratch | **None in current copy implementation** | No temporary-object ownership, atomic publish, rollback, or cleanup guarantee may be inferred |

`mutation_contains_dirty_path` canonicalizes target and each dirty path when possible, falls back to their given spelling on errors, and refuses equal paths or dirty descendants under the target. This preserves meaningful Windows ordinary/verbatim spelling behavior while leaving the observation/locking limits explicit. [S1:532–538]

### Actual GUI feedback

Planning/dispatch errors can populate `workspace.error`, which the GUI renders. Preview errors and counts are also shown. In contrast, `poll_folder_runtime` finds a `Completed` report with the current generation, clears `active_operation`, and calls `refresh_after_mutation(report.affected_subtree)`. It does not render/store `report.items` or `report.cancelled`. `refresh_after_mutation` ignores its subtree argument, clears the folder model and prepares a rescan while retaining view controls. Consequently a rescan is not a displayed per-item error or cancellation account. [S2:629–632,1124,1176,1249–1272,1448–1460]

Workers send one Completed event on normal return. `Progress` exists as a type but is not emitted by these spawn paths. The channel send result is ignored. The trash backend has panic sites at COM initialization/instance creation; a panic is not translated here into a failed-item report. This is source-level incompleteness of a guaranteed completion claim, not evidence that a panic or lost operation occurred. [S1:661–698,879–898; D2:39–42,272–318]

## 4. Resolved trash 5.2.4 Windows boundary

The manifest requests `trash` 5.2 with default features off and `coinit_apartmentthreaded`; the lock resolves **5.2.4**, using `windows` 0.56.0. The actual local registry source was inspected read-only; its hashes and exact locators are recorded in the inventory. No inference was made from the crate name alone. [S7:181; S8:5540; D1–D3]

1. `trash::delete` delegates through the default context to `delete_all`; `canonicalize_paths` canonicalizes the parent and rejoins the leaf, rejects a filesystem root, and preserves final-component link naming. This resolution occurs after Diff validation.
2. The Windows backend initializes COM using the enabled apartment-threaded feature and creates `IFileOperation`. It sets exactly `FOF_NO_UI | FOF_ALLOWUNDO | FOF_WANTNUKEWARNING`.
3. It removes an extended-path prefix for Shell parsing, calls `SHCreateItemFromParsingName`, and queues `DeleteItem` with no progress sink.
4. It calls `PerformOperations`. On success it queries `GetAnyOperationsAborted`; an aborted result becomes an error. A failed PerformOperations returns early as an error, without detailed completed-item enumeration. [D1:84–126,228–260; D2:39–76,272–318]

The documented flags request undo where possible and a warning when permanent destruction is contemplated. `FOF_NO_UI` combines silent/no-confirmation/no-error-UI/no-directory-confirmation flags; the warning flag partly overrides no-confirmation. This combination must not be simplified into either “guaranteed silent recycle” or “known automatic permanent delete.” `FOFX_RECYCLEONDELETE` is documented for Windows 8+ but is not set here; its existence is not a recommendation to change flags without compatibility evidence. [A9, A10]

Shell `DeleteItem` queues an `IShellItem`; `PerformOperations` performs the operation, and success alone can accompany an abort. The backend's additional abort check is material. It still returns `Result<()>`, not an approved-file-ID, recycle-location, or per-descendant receipt. The documents do not establish that this specific path-created Shell item remains bound to Diff's approved object across replacement. In the witness, substitution is placed **before Shell item construction**, avoiding an unsupported claim about Shell's later internal lookup timing. Later Shell behavior, actual recycle availability and share-mode compatibility remain native unknowns. [A11–A14]

## 5. Existing native capability and bounded alternatives

The selected native owner is Rename, not Diff. `prepare_guarded_rename_batch_native` validates root/parent proof chains, rejects reparse objects and mismatched native IDs/metadata, requires a same-parent rename, acquires and retains source/root/parent handles, and applies Rename's own content policy. Its `GuardedRenameFile::rename_to_leaf` revalidates the source and parent chain, calls `rename_open_file_no_replace`, then verifies the result. [S5:1150–1270,2942–3096,4725–4798]

The source handle requests `DELETE | FILE_READ_DATA | FILE_READ_ATTRIBUTES` and shares **read only**, using `OPEN_EXISTING`, `OPEN_REPARSE_POINT` and `BACKUP_SEMANTICS`. Directory guards request attribute access (plus enumeration when needed), share read/write **without delete**, and retain handles after identity/canonical-path checks. Sharing constraints last while handles are held; a final-component reparse-open flag does not by itself validate all ancestors. The explicit guarded-chain owner is important. [S5:6004–6052,9020–9096; A3]

`rename_open_file_no_replace` uses `SetFileInformationByHandle` on the held source with `FILE_RENAME_INFO`, `ReplaceIfExists=false`, an **absolute destination**, and **null `RootDirectory`**. The parent's handle is used for separate retained/revalidated guards and to derive the destination. This is not a relative-parent-handle rename implementation. Its historical fixture comment is not a native result for this spike. Non-Windows guarded rename is unsupported. [S5:8718–8805; A4–A8]

These obligations are not satisfied by the current no-replace rename alone. No scratch protocol is implemented or assumed here.

The exact later migration seam, if M2 recommends a stronger design, is `fresh` plus the `fs::copy`/post-copy permission path and the directory loop in `execute_copy`, and the validation-to-`TrashBackend` seam in `execute_delete`. GUI would continue dispatching captured plans; any per-item feedback change belongs to `poll_folder_runtime`/retained presentation state. Existing tests in the inventory would retain their invariants and gain deterministic injected pre/postvalidation refusal cases. There is no proposed migration of unrelated callers, persisted schemas, Rename journals, undo, or shared transaction machinery.

## 6. Evidence remaining before any stronger acceptance

- A required external-writer/product contract has not been established by this packet. Object binding and immutable-byte copying are different possible requirements.
- The exact native effect protocol for approved overwrite and guarded absent-target publication remains unproven. A held source alone is insufficient.
- Trash/Shell targeting under substitution, available recycling, flag interaction, partial directory effects and compatibility with retained guards have no native receipt here. No application fallback is a narrower established fact.
- The source proves executor result construction and GUI omission, not user observation of a successful/failing/cancelled native operation.

The [hand-reviewed tables](IDENTITY_PROOF.md) are sufficient for this milestone's representation/check-use argument. Optional executable model: **NOT_NEEDED**, zero invocations. Native execution: **NOT_RUN**. One conditional, disposable two-interleave protocol is specified there for any later decision that actually needs native evidence; no future implementation goal is created or executed.
